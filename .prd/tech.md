# Technical design

One Astro project with the Cloudflare adapter and one Worker. Prerender public content pages. Render the explicit GitHub routes and sign-in routes on request. Native links, forms, and `<details>` provide the interaction with zero client JavaScript. The service reads GitHub on demand and stores only sign-in sessions. It uses no project database or webhook. Use public dependencies and local assets with their licenses so a contributor can install, build, and test without private registry access.

## The GitHub App

The static site and fixture build work without GitHub credentials. Configure the read-only GitHub App for live repository access. Repository owners choose which repositories to install it on. Anonymous access requires an installed, opted-in repository that GitHub currently reports as public. Signed-in access uses a per-user GitHub App token. Its effective access is limited by the user's access and the App's installed repository access. Sign-in does not bypass either limit.

Keep the App manifest in the repository. Grant the minimum read permissions needed for repository metadata, issues, pull requests, configured process evidence, checks, statuses, and workflow runs. Configure the App's Single file grant with `single_file=read` and `single_file_name=.github/poludzku.yml` and read that file on the repository's default branch. Omit general Contents permission and all write permissions. Verify the required reads with an actual App installation on a private test repository with synthetic data, including that the App can read the configuration file and cannot read a second file. Treat evidence that needs broader access as unavailable. Derive callback addresses from deployment configuration and keep App credentials in Worker secrets.

Bind the authorization response to the sign-in attempt. Keep each session and its GitHub user token in a strongly consistent record, using a Cloudflare Durable Object in the same Worker for each opaque session identifier. The secure, HTTP-only cookie contains only that identifier. Authenticate each private request against that record, then check repository access with the viewer token. Keep session records and authorization decisions out of Workers KV and both the site and response caches. End the session at the earlier of token expiry and eight hours. Sign-out awaits durable deletion before reporting success and clears the cookie. A request that cannot verify its session receives no private data. Let the viewer sign in again after expiry without retaining a refresh token.

## Reads and cache

- Validate route inputs and resolve repository identity, visibility, and the relevant installation or viewer access before reading the cache or issuing a task redirect. Recheck current visibility and App access on every anonymous request, including a cache hit. If GitHub cannot verify either, withhold the data. A signed-in request uses only its viewer token for repository contents and links. Expose the same unavailable response for missing and unauthorized repositories when needed to avoid disclosing their existence.
- Use server-side `fetch` for the GraphQL and REST reads needed by the evidence contract. Follow pagination where results could affect task identity, selected pull request, latest effective marker or review, or checks on the current head. Bind reads to normalized repository and object identifiers. When a connection has more pages, a response is partial, or the time or request budget runs out, mark affected evidence incomplete. Handle rate limits and permission failures explicitly. An empty successful connection supplies different evidence from an inaccessible connection.
- Cache only anonymous snapshots of verified public data in the Workers Cache API for up to 60 seconds. Key by repository identity, route resource, and installation. Share data before localization, so PL and EN pages show the same snapshot. Run the access check before serving either layout. A change in visibility, installation, or access makes the old snapshot ineligible immediately. Keep viewer-derived responses and authorization or error results out of the shared cache. Send `Cache-Control: private, no-store` for dynamic GitHub and sign-in replies, including redirects and errors. Cache the eligible public snapshot inside the Worker, so every rendered response still passes the server access check.
- Treat API payloads, configuration, and GitHub text as untrusted input. Validate the config shape, escape task content, and generate links from verified GitHub object URLs. Keep credentials, cookies, private payloads, and raw process logs out of diagnostics and fixtures. Render a localized unavailable answer when a signal cannot be established.

## Lifecycle evidence

Use the authorized repository's Actions metadata, issue comments, pull request comments, and reviews to correlate the [Lifecycle signals](stages.md#lifecycle-preset). For an automated test submission, the writer's issue marker carries the spec hash. Its pull request step note, when present, supplies the writer run ID. Resolve that run through GitHub and require evidence tying the run and submission to the selected draft. If the note or run cannot establish the connection, mark the submission unknown. Consume only structured evidence. Raw log text stays on GitHub.

For implementation in progress, the trusted router accepts a `pull_request_review` event when an authorized reviewer submits a review beginning with `tests-ok` on the current draft head. The producer sets `stage=deliver` with the pull request number, ref, and SHA as internal workflow outputs. Its downstream job runs under the name `deliver` only after routing accepts the review. Use that running job from the verified workflow attempt as dispatch evidence only when GitHub's review and Actions metadata unambiguously associate it with that review, pull request, and full current draft head. Use the associated pull request head, since a workflow run SHA can refer to a merge commit. A router trigger, successful routing job, or matching job name alone leaves progress unknown. This path shows implementation underway while the lock attestation is still pending.

For test approval, trust the repository's Lifecycle gate only when GitHub metadata verifies the workflow identity, run attempt, selected pull request and current head. The run must come from the repository's trusted workflow. Matching display names or the GitHub Actions bot identity alone cannot prove that. Require a successful `Test lock` step and the explicit `locked at` result in the trusted producer's acceptance report. Match the report's run link and publication time to the run attempt and its `acceptance v1` marker to the full current head SHA. Resolve any abbreviated lock commit in the report against the candidate review's full `commit_id` without ambiguity. The attestation must follow the current spec approval and the candidate review. A successful step can report `not locked`, so the step result alone cannot establish test approval. A separate check failure can still affect health.

Use this attestation for authority instead of inferring it from review text. If the workflow source, scope, timing, selected review, or positive lock result cannot be verified with the existing read access, treat approval as unknown. The App needs neither access to `CODEOWNERS` nor a separate list of authorized reviewers.

## Implementation

| Area | Contract |
| --- | --- |
| `src/lib/stages.mjs` | Pure stage, health, mover, and evidence derivation defined in [stages.md](stages.md) |
| `src/lib/github.ts` | Server-only identity, access, pagination, and normalization of GitHub reads |
| `src/pages/gh/` | Project, task, and branch routes with PL and EN entry points defined in [product.md](product.md) |
| `src/pages/zaloguj/` | Sign-in start and callback. Sign-out ends the session |
| `src/locales/` | PL and EN interface copy, presets, and glossary |
| `src/content/` | Markdown home text and articles |

Test the derivation with `node --test` and the pages with Playwright using synthetic GitHub responses. Exercise incomplete reads, current-head changes, route canonicalization, keyboard interaction, and isolation of private or viewer-derived data. Include a warmed public cache followed by visibility or installation loss, an expired session, and a second viewer who cannot access the first viewer's repository. Use two independent Worker instances bound to the same session namespace. Verify a private read succeeds through the second instance with the test cookie, sign out through the first instance, and replay the same cookie through the second. The replay must return no private data. Use fixture data created for tests and examples.

## Budgets

Task page under 30 KB total HTML and CSS, 0 KB JavaScript, and LCP under 1.5 seconds on a cached view. Lighthouse accessibility score 100. Keep the measurement conditions consistent across runs. See [interface.md](interface.md) for keyboard and mobile acceptance.
